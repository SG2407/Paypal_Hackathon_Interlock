# 1. PROJECT VISION

Product name: IntentLock

Tagline: "Your AI can shop. You control what it can buy."

IntentLock is an AI-powered transaction intent and authorization layer designed for PayPal's agentic commerce ecosystem.

Problem:

AI shopping agents can search, compare, recommend, and initiate purchases. However, they can select products that violate the buyer's actual instructions.

Examples:

- Buying a refurbished product when the customer requested a new one.
- Exceeding the buyer's total budget after shipping and tax.
- Adding an unwanted recurring subscription.
- Purchasing an alternative product without permission.
- Increasing the checkout price after the original purchase request.
- Purchasing an item that will arrive after the customer's deadline.

IntentLock converts natural-language buyer instructions into a structured purchasing permission policy.

An AI shopping assistant can recommend and prepare products, but a separate deterministic policy engine must check the actual purchase before it can proceed to PayPal payment capture.

The system must have three possible decisions:

1. PASS — The order satisfies all mandatory requirements and can proceed to buyer approval.
2. REVIEW — The purchase contains uncertainty or requires additional buyer permission.
3. BLOCK — A mandatory constraint is violated. Payment capture must not happen.

Core product principle:

**The AI can recommend purchases. The deterministic policy engine controls purchasing permissions. The buyer retains final authorization.**

This is a prototype of a PayPal product capability, not a generic ecommerce store.

## 6. MOST IMPORTANT: PRE-CAPTURE VALIDATION

Implement:

POST /api/orders/[orderId]/capture

This endpoint is the core security component.

Never capture money merely because the frontend says that checkout was approved.

Server-side steps:

1. Find the PayPal order in the local database.
2. Find its associated shopping mission.
3. Load the exact confirmed permission-policy version.
4. Load the original server-generated purchase snapshot.
5. Retrieve the actual PayPal order from the Sandbox REST API using the order ID.
6. Verify that the PayPal order belongs to the application's stored order record.
7. Verify that PayPal reports the order as APPROVED.
8. Compare the actual order amount against the saved server-generated amount.
9. Verify currency.
10. Verify each item, quantity and SKU where available.
11. Compare actual PayPal order details with the stored purchase snapshot.
12. Re-run the deterministic permission engine.
13. Check that the permission has not expired.
14. Verify that the human buyer approval step has occurred.
15. If any mandatory check fails, return HTTP 409 with an explicit reason and DO NOT capture.
16. Only if every check succeeds, call the actual PayPal capture endpoint.
17. Verify the PayPal capture response.
18. Save the actual capture ID, transaction status, final amount and timestamp.
19. Record a final audit event.
20. Show the completed sandbox transaction in the UI.

Implement idempotency.

Repeated capture requests must not accidentally create duplicate payments. If the order was already captured, retrieve and return its saved capture result rather than attempting a new capture.

Do not accept PayPal order IDs that do not exist in the application's own database.

Do not implement automatic capture without buyer approval.

# 10. DETERMINISTIC POLICY ENGINE

Create an independent policy engine module.

Use strict TypeScript types.

Possible input:

- Confirmed permission policy.
- Product record.
- Server-generated cart details.
- Current time.
- Optional PayPal retrieved order details.

Possible result:

{
  decision: "PASS" | "REVIEW" | "BLOCK",
  violations: [],
  warnings: [],
  checks: [],
  evaluatedAt: "...",
  policyVersion: "..."
}

Use the following logic:

BLOCK:
- Total exceeds maximum budget.
- Wrong currency.
- Refurbished product when new is required.
- Prohibited subscription exists.
- Unauthorized add-on exists.
- Delivery after mandatory deadline.
- Unauthorized product substitution.
- Permission expired.
- Product is missing.
- Actual order total does not match the stored purchase.
- Actual PayPal line items do not match the original order.
- Order is not approved.
- Buyer approval is not recorded.

REVIEW:
- Product attribute information is missing.
- Important buyer instruction is ambiguous.
- Alternative product requires permission.
- Merchant identity is uncertain.
- Product information cannot be verified.

PASS:
- All mandatory restrictions are satisfied.
- Required information is available.
- The total is within budget.
- The product satisfies the approved policy.
- The mission is valid and unexpired.

Do not allow missing data to default to PASS.

Write unit tests for every rule.
